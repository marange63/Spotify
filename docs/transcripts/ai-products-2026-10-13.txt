The model headlines this week are mostly reruns on this beat. The real movement is in the plumbing underneath the models. Two questions sit there: what an AI agent is allowed to touch, and who gets to decide which model it runs. Three items this week answer them in three different directions, and that's today's spine.

Start with GitHub. GitHub has made local sandboxing for its Copilot agents generally available, at no extra cost. The sandbox limits what an agent can touch across files, network resources, and credentials on the developer's own machine. This beat has spent the past week flagging coding agents that run without that kind of containment. So this is the first real containment control we've seen actually ship on that thread.

Read the scope narrowly, though. This is local sandboxing, for agents running on your own machine. It does nothing for GitHub's cloud-hosted computer-use agent, which is where we flagged the missing permissioning model last week. So this advances the thread. It doesn't close it.

And even locally, the defaults matter more than the headline. GitHub's documentation for the Copilot app is specific: sandboxing is, quote, "turned off by default unless enterprise managed settings require it." A developer has to switch it on, or the organization has to mandate it. When an admin does mandate it, the developer can't change those settings. And enterprise rules, in GitHub's words, "can only narrow your allowlist, never widen it."

Even once it's on, the sandbox is more permissive than the word implies. According to GitHub's docs, outbound internet access stays open by default. It isn't blocked or allow-listed out of the box. And the Copilot app and the Copilot CLI keep their sandbox settings separately. GitHub says plainly that changing them in one does not change them in the other. So a developer who locks down the app has done nothing for the CLI. Those two are also the only surfaces GitHub's sandbox docs describe.

So the honest description is that containment moved from nonexistent to available. It did not move to on by default. Whether this is GitHub leading or catching up to a baseline other coding agents already meet, nothing I've seen settles. Nor are there any adoption figures for how many teams have switched it on. For enterprise security teams, the procurement question shifts. It used to be "can we contain this agent at all." Now it's "did we actually turn containment on, on every surface." That's real progress, but the burden sits with the buyer, not the vendor.

The same release hands developers a second control: the choice of model. The Copilot CLI's model picker can now discover models from a running local Ollama instance, alongside the cloud options. GitHub's docs say no API key is required for a provider like Ollama that doesn't use authentication. My inference is that this makes hybrid cloud-plus-local inference a normal option for teams with data-residency limits, though there's no adoption evidence yet.

But don't read "local model" as "private." GitHub's own documentation warns that if the configured endpoint points to a remote server, "your prompts and code context are still sent over the network to that provider." Real isolation needs GitHub's separate offline mode and an endpoint that genuinely is local. One smaller fix rides in the same changelog. The Copilot app now lets a developer use one GitHub account for the Copilot license and another for repositories, which removes a real friction point in enterprise onboarding.

So the GitHub story is this. Developers got a containment switch and a model choice, and GitHub left the job of using both to the customer.

Now the opposite direction. Where GitHub hands the model decision to the developer, Google is making it for them. Google's Gemini API changelog says gemini-3.7-flash "is deprecated," and that "all requests to gemini-3.7-flash are automatically routed to gemini-3.8-flash." Most callers probably benefit without noticing, and there's no evidence of harm. The cost lands on teams that pinned that model ID for evaluation stability, because their outputs can now shift with no code change. So here the vendor picks the model, and watching for that becomes the buyer's job.

The third answer to who controls the agent layer comes from outside developer tools entirely, and it's the most strategically interesting of the three. On October 6th, OpenAI and Atlassian expanded their partnership to bring GPT-6 family models across Atlassian's platform and its Rovo assistant. We haven't covered it on this beat until now. GPT-6, OpenAI's current flagship model family, is old news here. What's new is how the two companies described the division of labor. Quote, "OpenAI supplies the reasoning capabilities, while Atlassian's Teamwork Graph provides organizational context." In plain terms, OpenAI brings the thinking. Atlassian brings the map of a company's tickets, documents, and teams.

That's the reverse of a Salesforce move we covered last week. Salesforce built its own reasoning model for CRM work, called Koa, and let other vendors' chat windows own the interface. Atlassian makes the opposite trade. It outsources the reasoning layer, and keeps the organizational context for itself. So two large software incumbents each decided to keep one layer, and they picked different ones. That's the useful pattern for anyone judging SaaS incumbents right now. The question isn't whether they built a model. It's which layer they refused to give up.

Look at it from OpenAI's side too. OpenAI is effectively a tenant here, running inside Jira and Confluence under someone else's brand. That's a different distribution play from winning ChatGPT seats. My read is that it gets OpenAI's models into daily enterprise workflow without OpenAI owning the customer relationship. The trade-off is that the landlord sets the terms.

Some guardrails on how far to take this. It's a partnership announcement, not proof of deployment. There are no disclosed financial terms, no named customers, and no usage data. Sources also disagree on whether agents can pick up Jira tickets autonomously today, or whether that's still exploratory. So treat autonomous ticket-handling as unconfirmed, not shipped. And nothing establishes that GPT-6 is Atlassian's exclusive model supplier. It may simply fill one slot among several.

The structural point stands regardless, and it's my inference. If the organizational graph is where an agent's real value sits, the model underneath it is the more substitutable piece. That gives Atlassian, the platform owner, the pricing leverage, rather than the lab supplying the reasoning.

So pull it together. Control over the agent layer split three ways this week. The developer got a sandbox switch and a local-model option from GitHub, both opt-in, and both more permissive by default than their names suggest. The vendor, Google, made the model choice itself through deprecation routing. And Atlassian, the platform owner, kept the organizational context and treated the frontier model as a supplier. Keep the status straight, too. GitHub's sandboxing is generally available, Atlassian's deal is an announced partnership, and Google's routing is already live. None of the three comes with adoption data.

Three things to watch from here. First, whether GitHub makes sandboxing the default rather than an admin's choice. Second, whether Google gives pinned-model teams more warning before the next forced routing. Third, whether Atlassian names production customers running GPT-6 inside Rovo.

Good morning. It's Sunday, August 23rd, and this is your AI products briefing.

This week this show tracked what agents can do, then what running them costs, then who gets paid when they act. Today the variable that shipped is permission: who, or what, is actually allowed to act.

Start with the protocol layer. On August 22, the Model Context Protocol steering group published its next roadmap, and the headline items aren't features. They're admissions of what's still broken. Four weeks earlier, on July 28, the same group shipped a stateless protocol core, which let an MCP server sit behind an ordinary load balancer instead of needing sticky sessions. That's the one clause of context you need. What's new is what they published next. There is still no standardized way for an agent to prove who it is. Clients still poll for long-running results, and the roadmap prioritizes server-initiated events so they stop having to. And the group has now admitted, in writing, that a server exposing a hundred tools forces the model to pay the context cost of the entire toolbox before the user has asked a single question.

Take the identity piece first, because it collided with something this show said yesterday. On Saturday we described Google's Agent Identity system already running in production at a named retailer, and argued that whoever standardizes machine identity for agents holds the lock-in position in enterprise AI. The MCP roadmap, published that same day, puts a vendor-neutral version of that exact primitive at the top of its list. In its own words, the steering group wants MCP servers to have "a standardized way to recognize and trust those agent identities, built on existing standards rather than pasted API keys and long-lived tokens."

Their diagnosis of the current failure is specific. MCP authorization today, they write, "is built around a person approving access in a browser." That breaks down, in their words, when the callers are "agents running as cloud workloads with their own identity, acting on behalf of a user who isn't present." And the proposed fix is not a new invention. The roadmap routes agent identity through machinery enterprises already run: finalizing an existing standard called Demonstrating Proof of Possession, then an opinionated path through workload identity federation and standard token exchange. That's a meaningfully stronger bet than a proprietary system built by one vendor, because it doesn't ask an enterprise to trust a single cloud's permissions model. It asks them to extend identity infrastructure they've already deployed. If that lands, existing IAM and zero-trust tooling covers agents by extension. That removes a named procurement blocker in regulated industries, and it erodes most of the lock-in value sitting in any one cloud's proprietary agent-permissions system.

Two caveats before moving on. This is a roadmap, not a ratified spec. Read end to end, it gives no target date, no version number, and no ratification process for agent identity or for server push. And neither the roadmap nor anything else in the record says how many production MCP servers actually migrated to July's stateless core in the four weeks since. So the standards body is naming the right problem. It hasn't shown it can move fast enough to solve it.

The tool-catalog admission matters for a separate reason: cost. The steering group's own words are blunt. Connecting to a server with a hundred tools, they write, "means the model pays for that entire surface before the user has asked a single question." That's not an ergonomics complaint. It's a per-request inference tax on exactly the agent loops enterprises run most. And fixing it changes a budget decision, not a latency one. Today, every additional internal tool you expose to an agent raises the cost of every call, so enterprises keep their MCP surface deliberately narrow. Remove that tax and wide internal tool exposure becomes economically rational, not merely technically possible.

Which brings us to the number that makes all of this urgent rather than theoretical. On August 13, OpenAI published usage data from its own enterprise customers. It's the first hard enterprise-demand figure this show has had in a week of protocol and pricing stories. As of June 2026, OpenAI reports, agentic use of its Codex product "accounted for 64% of combined Codex and ChatGPT output tokens among enterprise customers." Read that plainly. Inside real enterprise deployments, most output volume is no longer chat-style question and answer. It's agents executing multi-step tasks on their own.

Now take that number with real skepticism. This is OpenAI measuring OpenAI, with a commercial interest in pushing customers toward Codex, and using its own definitional choice that Codex tokens equal agentic use. The figure is two months stale, and it reached us through a single secondary outlet because OpenAI's own report page has been inaccessible. OpenAI also describes a widening gap between its heaviest enterprise users and typical companies, but the specific multiple behind that claim couldn't be matched to OpenAI's own text, so treat it as directional only. Most importantly, output tokens measure volume, not value. Agent loops emit far more tokens per unit of real work than a chat reply does, by construction. Sixty-four percent of output tokens is not sixty-four percent of the work.

What the figure does establish credibly is direction: delegation is growing relative to assistance. Two things follow from that. The identity gap the MCP roadmap just named is a live exposure across the majority of enterprise AI volume, not a problem to solve at leisure. And seat-based SaaS pricing is structurally mismatched to this, because an agent consumes tokens rather than seats. Vendors who have converted to metered agent billing capture that growth directly. The ones still selling licenses watch the work migrate to a meter they don't own.

Machine authorization is one half of the permission story. The other half is a human deciding whether to let the agent's work actually land, and that shipped this week too. On August 20, Slack launched Slack Code. Mention a supported coding agent from any conversation, and it spins up a project-scoped channel where the agent proposes a plan, writes the code, shows diffs and live previews, then archives itself into a searchable audit trail once merged. Slack says it is live today for teams using Claude, Devin, GitHub Copilot and Vercel, with OpenAI coming soon. That's the notable choice. Slack didn't pick one agent, it hosts four competing ones, positioning itself as the neutral collaboration layer for a stack it doesn't own. It also continues an arc this show has tracked all week: the bottleneck in agentic coding keeps moving further from writing code, to integration and merge on Thursday, to taking the action on Friday, and now to team-level approval and audit.

Apply the rebrand test, though, because most of this is a channel wrapper around agents you must already license separately. The genuinely new thing here isn't code generation. It's that a product manager can watch and approve an agent's change without opening a terminal, and that the audit trail exists by default. Read the adoption stat skeptically too. Slack says "over 70% of code channels spin up and close within a single day, from idea to merged PR." That sounds like frictionless delivery. It's equally consistent with small, well-scoped changes, the class of work that was already cheap before agents showed up. It isn't evidence that agents are handling the large, cross-cutting changes where review actually costs a team something. No separate pricing is disclosed, and no named customers came with the launch. The competitive read is simpler: if the review-and-approve step moves into Slack, GitHub has to deepen Copilot's own team-review surface or cede the part of the workflow developers can least afford to get wrong.

Close with the consumer version of the same architecture. On August 18, OpenAI rolled out ChatGPT for Teens, a distinct, age-gated product for thirteen to seventeen year olds, with default-on restrictions rather than opt-in filters. Its Study Mode offers, in OpenAI's language, "guiding questions and step-by-step support to help them understand the material," plus reminders that appear "when a teen appears to be trying to cheat, instead of understanding the material." Parents get account-level controls to "manage settings, receive safety notifications, and set Quiet Hours." On Friday this show argued that consent was the gate still closing. This is that gate shipping as product: not a filter you opt into, but a separate, permissioned account by default. Treat the guardrails skeptically. The age-verification mechanism isn't described anywhere in available reporting, the cheating nudge is a behavioral prompt rather than an enforcement wall, and this launch is at least as much litigation-risk mitigation as product strategy. But when the category leader ships default-on age segmentation, it sets a floor every rival with a teen user base has to match, which converts one company's legal exposure into an industry-wide product requirement.

One standing caveat, because it has now run most of this week. Both load-bearing numbers today are vendor-reported, with no independent audit trail behind either one.

So here's the through-line. What shipped this week wasn't new capability. Enterprises already had agents that could code, browse and act. What shipped is the permission layer being built underneath capability that already exists, at the protocol level, the team level and the consumer account level, all at once. That's the real story, and it's still being written by the vendors it benefits most.

That's the briefing. Talk to you tomorrow.
